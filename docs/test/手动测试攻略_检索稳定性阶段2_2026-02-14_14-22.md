# 手动测试攻略（检索稳定性阶段2）
记录时间：2026-02-14 14:22

## 0. 前置准备
1. 启动容器：
   `docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build backend frontend postgres redis`
2. 核验服务：
   `docker compose -f docker-compose.yml -f docker-compose.gpu.yml ps`
3. 打开前端：`http://localhost:3000`

## 1. 场景A：上传文档后不再长期“处理中”
1. 登录任意测试账号。
2. 进入“知识库”页面，创建一个新知识库。
3. 上传一个 `.txt` 文件（建议 100~1000 字）。
4. 观察文档状态。

预期结果：
- 状态在合理时间内从“处理中”切到“完成”或“失败”。
- 不应长期卡在“处理中 + 分片=0”。

## 2. 场景B：检索链路可返回结果
1. 在该知识库内发起搜索（关键词来自刚上传文档正文）。
2. 开启默认检索配置（Query Rewrite / Hybrid / Reranker / Compression）。

预期结果：
- 返回至少 1 条命中结果。
- 结果卡片可正常展开内容，无空白。

## 3. 场景C：查看检索元信息（前端可感知）
1. 在结果卡片点击“展开检索元信息”。
2. 关注以下字段：
   - 检索维度 `retrieval_dimension`
   - 改写缓存命中 `query_rewrite_cache_hit`
   - 改写跳过原因 `query_rewrite_skip_reason`
   - 压缩状态 `contextual_compression_enabled`

预期结果：
- 字段存在且随查询策略变化。
- 小库场景可看到 `retrieval_dimension=256`。

## 4. 场景D：相邻上下文能力
1. 打开“相邻上下文”开关，窗口设为 1 或 2。
2. 发起搜索并展开卡片中的相邻上下文区块。

预期结果：
- 可看到 `adjacent_context` 内容列表。
- 关闭开关后，该区块不展示。

## 5. 场景E：失败可见性
1. 上传一个故意异常文件（如损坏 PDF）。
2. 观察文档状态与错误信息。

预期结果：
- 最终状态应为“失败”，并有可读错误提示。
- 不应出现“后台失败但前端一直处理中”。

## 6. 故障排查（按顺序）
1. 看容器是否最新：
   `docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build backend frontend`
2. 看后端日志关键字：
   `docker compose -f docker-compose.yml -f docker-compose.gpu.yml logs --tail 200 backend`
   重点检索：`different vector dimensions`、`处理文档失败`、`文档处理完成`。
3. 看迁移版本：
   `docker exec research_postgres psql -U yui -d research_assistant -c "select version_num from alembic_version;"`
   预期：`014_drop_legacy_hnsw`
4. 看索引是否正确：
   `docker exec research_postgres psql -U yui -d research_assistant -c "\d+ document_chunks"`
   预期：存在 `ix_chunks_embedding_hnsw_256/512/1024`，无旧 `ix_chunks_embedding_hnsw` 全局索引。

## 7. 建议验收口径
- 至少完成 1 次“上传 -> 完成 -> 检索命中”闭环。
- 至少完成 1 次“失败 -> 前端可见失败”闭环。
- 检索元信息可见并与策略一致。
