# 自适应维度策略评估

- 日期：`2026-03-30`
- 阶段：`retrieval ablation`
- 状态：`done`

## 问题

当前知识库默认使用：

- `embedding_dimension_policy = adaptive`
- 小库：`256`
- 中库：`512`
- 大库：`1024`

实现位置：

- [config.py](/mnt/d/codefield/agent-platform/research-assistant/backend/app/config.py)
- [embedding_dimension_policy_service.py](/mnt/d/codefield/agent-platform/research-assistant/backend/app/services/embedding_dimension_policy_service.py)

当前策略按 `paragraph chunk` 总量决定维度，并带 hysteresis。

## 当前观察

基于公开 `BEIR / SciFact` 子集的当前结果：

- `1024` 维：排序质量最好
- `512` 维：次之
- `256` 维：`Recall@10` 基本可接受，但 `NDCG/MRR` 明显下降

当前结论不是“实现有 bug”，而是：

- 当前 Matryoshka 截断实现较朴素：完整向量 -> 前缀截断 -> 归一化
- 当前自适应策略更偏“成本优先”，不是“质量优先”

## 暂定判断

当前结果不支持把 `adaptive` 直接判成错误设计。

更准确地说：

- 这套策略确实更偏“成本优先”，不是“质量优先”
- 但在当前样本上，`256 / 512` 带来的排序损失属于**可见但可接受**的工程折中
- 如果系统目标允许用少量 `NDCG/MRR` 损失换取更低的存储和检索成本，这个策略仍然成立

## 等待后续消融回答的问题

1. `1024 / 512 / 256` 在更大公开集上的差异是否稳定
2. `hybrid / rerank` 加入后，低维排序损失是否仍明显
3. 当前生产链到底更偏“质量优先”还是“成本优先”
4. 是否应收敛到：
   - `fixed + 1024`
   - 或 `adaptive` 但上调默认档位

## 暂不执行的动作

- 不立即把默认策略改成 `fixed`
- 不立即删除 `adaptive`
- 不立即重建历史知识库维度

## 当前决定

- 单因素结果已经够明确：`1024 > 512 > 256`
- 但当前也没有证据说明 `256 / 512` 的排序损失已经大到不可接受
- 因此这项暂时不作为当前检索优化主问题
- 当前更合理的定位是：
  - `1024`：质量优先基线
  - `adaptive`：可接受的成本优先策略
- 后续组合消融阶段，不再把 `adaptive` 当成优先处理项，除非真实业务 query 再暴露出明显质量问题
