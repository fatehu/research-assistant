- 阶段：`retrieval ablation`

## 问题

当前知识库搜索主链支持 cross-encoder rerank。

实现位置：

- [reranker_service.py](/mnt/d/codefield/agent-platform/research-assistant/backend/app/services/reranker_service.py)

需要判断：

- rerank 是否值得作为默认增强项
- 它提升的是顶部排序质量，还是对召回也有明显帮助
- 它带来的延迟是否可接受

## 当前观察

## 正式结果

### 结果 A：最小 smoke（dense-only 候选）

当前第一版正式结果来自最小 smoke：

- 数据集：`SciFact`
- 样本：`3 queries / 28 candidate docs`
- 候选：复用已有 dense runfile 的 `candidate_k=10`
- 结果文件：
  - [metrics.json](/mnt/d/codefield/agent-platform/research-assistant/backend/eval/retrieval_beir/output/scifact/20260330-072759-backend-rerank-smoke/metrics.json)

baseline（dense）：

- `NDCG@10 = 0.83333`
- `Recall@10 = 1.0`
- `MRR@10 = 0.77778`

`dense + rerank`：

- `NDCG@10 = 0.78540`
- `Recall@10 = 1.0`
- `MRR@10 = 0.72222`

运行特征：

- `warmup_ms = 53813.6`
- `rerank_eval_ms = 3837.64`

### 结果 B：backend hybrid + rerank smoke

在切换轻量英文 reranker 后，又补了一轮更贴近当前主链的 smoke：

- reranker 模型：`Alibaba-NLP/gte-reranker-modernbert-base`
- baseline：backend 风格 `hybrid + RRF`
- rerank：backend 容器内真实 `RerankerService`
- 数据集：`SciFact`
- 样本：`20 queries / 200 corpus`
- 候选：`candidate_k=8`
- 结果文件：
  - baseline：
    - [metrics.json](/mnt/d/codefield/agent-platform/research-assistant/backend/eval/retrieval_beir/output/scifact/20260330-185902-backend-hybrid-dim1024/metrics.json)
  - rerank：
    - [metrics.json](/mnt/d/codefield/agent-platform/research-assistant/backend/eval/retrieval_beir/output/scifact/20260330-110110-backend-rerank-smoke/metrics.json)

baseline（backend hybrid）：

- `NDCG@1 = 0.95`
- `NDCG@3 = 0.94599`
- `NDCG@5 = 0.94599`
- `NDCG@10 = 0.96176`
- `MRR@3 = 0.95`
- `MRR@5 = 0.95`

`backend hybrid + rerank`：

- `NDCG@1 = 0.95`
- `NDCG@3 = 0.98155`
- `NDCG@5 = 0.98155`
- `NDCG@8 = 0.98155`
- `MRR@3 = 0.975`
- `MRR@5 = 0.975`

运行特征：

- `warmup_ms = 93563.84`
- `rerank_eval_ms = 21481.46`
- `query_count = 20`
- `candidate_k = 8`

## 当前结论

- 在最早那轮 `dense-only` 最小样本上，旧 reranker **没有带来收益**
- 但在更贴近当前主链的 `backend hybrid + rerank` smoke 上，rerank 对 `@3/@5` 的排序质量有明确正向收益
- 当前收益更像“整理前几条结果”，不是扩大召回
- 延迟仍然偏高：
  - 冷启动接近 `94s`
  - `20 queries / candidate_k=8` 的 rerank eval 仍约 `21.5s`

## 当前决定

- rerank 单因素消融已经完成
- 当前信号支持：`rerank` 作为高质量模式是有价值的
- 当前信号仍不足以支持把 rerank 当默认增强项
- 后续重点不再是“有没有收益”，而是“收益是否值得当前延迟”

## 等待后续消融回答的问题

1. `dense` 与 `dense + rerank` 在公开集子集上的 `NDCG / MRR` 差异
2. rerank 的边际收益在 `hybrid` 叠加后是否仍明显
3. rerank 的冷启动和常驻延迟是否能接受

## 暂不执行的动作

- 不立即修改 `enable_reranker` 默认值
- 不把 rerank 自动并入默认搜索路径
