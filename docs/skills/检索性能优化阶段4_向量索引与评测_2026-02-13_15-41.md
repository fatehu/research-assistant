# 检索性能优化阶段4：向量索引与评测闭环

- 记录时间：2026-02-13 15:41
- 阶段：Phase 4（提交 4）

## 使用了哪些技术
1. 自适应 `ef_search`：`resolve_ef_search(total_chunks, dimension)`，按语料规模与向量维度动态计算查询参数。
2. 双链路接入：在 API 检索链路与 Agent Tool 检索链路统一应用动态 `ef_search`。
3. 可执行评测脚本：`backend/app/maintenance/eval_retrieval_recall.py`，支持 1024/512 对比、门槛判定、失败返回非 0。
4. 评测数据集：新增 `backend/tests/data/retrieval_eval_cases.v1.json`（30 条真实查询用例）。

## 目的是什么
1. 建立“检索参数调优 -> 可量化评测 -> 门槛判定”的闭环。
2. 在不切生产主线维度（仍 1024）的前提下，给出 512 维可观测对比结论。

## 怎么用
1. 运行评测：

```bash
python -m app.maintenance.eval_retrieval_recall \
  --cases backend/tests/data/retrieval_eval_cases.v1.json \
  --top-k 10 \
  --dims 1024,512 \
  --score-repeat 128 \
  --latency-corpus-multiplier 16 \
  --baseline-dim 1024 \
  --target-dim 512 \
  --gate-max-recall-drop-pct 3 \
  --gate-min-latency-improve-pct 15 \
  --fail-on-gate
```

2. 结果报告落盘到 `docs/test/阶段4检索评测报告_2026-02-13_15-38.md`。

## 做到了什么
1. API 与 Tool 两条检索链路均接入动态 `ef_search`。
2. 产出 30 条完整评测集，不再使用占位 expected id。
3. 严格门槛评测通过：
   - recall@10 降幅：`0.0%`（<= 3%）
   - 检索延迟改善：`78.1044%`（>= 15%）

## 怎么感知效果
1. 日志可观测：检索日志带 `ef_search`、`corpus_size`。
2. 报告可观测：同一数据集下 1024/512 的 recall、MRR、延迟对比与门槛结果。

## 限制与说明
1. 当前语料规模较小（本地 256 向量），延迟评测使用 `latency_corpus_multiplier` 放大以降低抖动。
2. 生产默认维度仍是 1024；512 仅作为评测对比，不直接切主线。
