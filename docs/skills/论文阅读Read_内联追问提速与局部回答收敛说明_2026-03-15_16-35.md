# 论文阅读 Read 内联追问提速与局部回答收敛说明

时间：2026-03-15 16:35

## 背景

`/read` 的 `+ 段落追问` 当前存在两个明显问题：

- 首次可见响应慢
- 明明有局部证据时，也容易被 prompt 推向“证据不足，请去右侧询问”

同时，前端对 `disabled` 事件没有显式消费，导致用户有时体感为“点了没结果”。

## 本轮目标

- 优先使用当前页已有 compose cache，避免 inline query 触发不必要的整页 compose 构建
- inline query 改为真实 token 流式返回，而不是后端整段生成完再假流式切片
- prompt 从“拒答优先”收敛为“局部回答优先、范围提示明确”
- 前端显式处理 `disabled` 事件，避免无反馈

## 约束

- 不改 `/read` evidence 主链
- 不改节点 `source_block_ids / source_anchor_refs`
- 不扩大到右侧 `询问工作区`
- 不改变 inline query 的局部定位本质，仍只基于当前节点与邻近上下文回答

## 方案

### 1. payload 读取收敛

`build_inline_answer_card` / inline query 预处理优先读取：

- `get_latest_cached_payload_only(...)`

只有当前页没有 compose cache 时，才回退：

- `build_or_get_composed_payload(...)`

这样可以避免用户已经打开并生成过当前页时，段落追问还要重新走一遍 compose 主链。

### 2. 真流式输出

新增 inline query 专用的 prompt 构造与 `chat_stream(...)` 路径。

- 后端 SSE 在拿到 context 后立即开始透出 token
- 不再先等待完整答案再按 42 字符分片伪造流式

### 3. prompt 收敛

由原先的：

- 强约束两句输出
- 强约束证据不足时直接拒答

改为：

- 优先回答局部问题
- 允许给出“局部结论 + 范围限制”
- 只有上下文确实缺关键信息时，才明确说当前局部证据不足

### 4. disabled 显式反馈

前端收到 `disabled` 事件时：

- 立即提示用户
- 并插入一个 AnswerCard 说明为什么当前节点不可追问

避免“点击后无结果”的体验。

## 风险

- 使用 latest cached payload 时，若用户刚切换了局部主题/细节设置但当前页未重新生成，inline query 上下文可能基于旧 cache。
- 但这比每次重跑 compose 的代价更可控，也更符合 inline query 的局部追问定位。

## 回退点

如需回退，仅需恢复：

- inline query payload 读取方式
- inline query SSE 流式逻辑
- inline query prompt 文案
- frontend `disabled` 事件处理
