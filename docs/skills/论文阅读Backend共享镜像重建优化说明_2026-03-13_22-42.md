# 论文阅读 Backend 共享镜像重建优化说明

时间：2026-03-13 22:42

## 背景

当前 `docker compose up -d --build backend` 的真实成本仍然偏高。虽然已经通过 `backend/.dockerignore` 将 build context 从约 `2.03GB` 降到约 `14.60MB`，并恢复了 `docker-entrypoint.sh` 的 LF 行尾，同时把 `TORCH_INDEX_URL` 默认切回 `cu121`，但仍有一个明显的重复开销：

- `backend`
- `codelab-runner`
- `mcp_web`
- `mcp_literature`

这几个服务都复用同一份 `backend/Dockerfile` 和同一套 Python 运行时依赖，但当前 Compose 仍为它们分别声明了 `build`。

## 问题

即便只执行 `docker compose up -d --build backend`，Compose 在构建链上仍可能拉起同类镜像构建逻辑，导致：

- 同一份 CUDA torch wheel 和 Python 依赖被重复处理
- backend-only 的重建体感变慢
- 排障时很难判断“慢”是因为真正的 backend 镜像，还是因为同构服务也被卷进来

## 目标

在不改变服务职责的前提下，统一 backend 系服务镜像来源：

- `backend` 继续是唯一 build owner
- `codelab-runner`
- `mcp_web`
- `mcp_literature`

改为直接复用同一镜像，不再各自定义 `build`

## 方案

### 1. backend 成为共享镜像生产者

在 `docker-compose.yml` 的 `backend` 服务上显式声明共享镜像名，例如：

- `image: research-assistant-backend:latest`

并保留它自己的：

- `build.context`
- `build.dockerfile`
- `build.args.TORCH_INDEX_URL`

### 2. 同构服务改为直接引用镜像

以下服务改成只写：

- `image: research-assistant-backend:latest`

不再单独保留 `build`

- `codelab-runner`
- `mcp_web`
- `mcp_literature`

### 3. 保持运行时差异只在 command / env

共享镜像不代表共享命令。各服务仍保留自己当前的：

- `command`
- `ports`
- `profiles`
- `environment`

### 4. 不触碰 frontend / postgres / redis

这轮只优化 backend 系服务镜像复用，不改其他服务。

## 风险与回退

### 风险

- 如果某个同构服务未来真的需要不同系统依赖，共享镜像会限制它单独演化
- CI 若默认假设这些服务各自 build，可能需要同步检查配置兼容性

### 回退

如果共享镜像策略引发问题，回退方式很直接：

- 恢复 `codelab-runner / mcp_web / mcp_literature` 的 `build` 段
- 删除 `backend.image`

## 本轮不做的事

- 不调整 `frontend` 构建策略
- 不移动仓库到 Linux 原生盘
- 不处理 runtime GPU 可见性，只处理镜像构建复用
