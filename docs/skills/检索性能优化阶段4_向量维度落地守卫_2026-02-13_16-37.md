# 检索性能优化阶段4：向量维度落地守卫

- 记录时间：2026-02-13 16:37
- 目标：把阶段4从“仅评测”推进到“在线链路可控落地”，避免维度切换时出现混维误检索或报错。

## 本次技术点
- 检索维度守卫（API + Tool 双链路）
  - 向量检索 SQL 增加 `embedding_dimension = :vector_dimension` 过滤。
  - `vector_top_k` 检索与语料规模统计（count）统一按同维度过滤。
- 入库维度显式写入
  - 文档处理入库时，primary chunk 通过 `len(embedding)` 写入 `embedding_dimension`。
  - context chunk 写入当前 embedding 服务维度，避免依赖默认值造成漂移。
- 可观测性增强
  - 检索结果 metadata 新增 `retrieval_dimension`。
  - 检索日志新增 `dim` 维度字段。
- 回归测试增强
  - 扩展 `test_tool_registry_knowledge_search.py`，新增 API/Tool 维度过滤断言。

## 目的
- 让 1024/512 切换具备工程可控性，而不是仅靠配置“盲切”。
- 避免维度不一致导致的检索污染、性能误判和线上不稳定。

## 怎么用
1. 默认维度（1024）下无需额外操作，链路自动生效。
2. 计划切换 512 时：
   - 先运行阶段4评测脚本并看 gate。
   - 再执行重建脚本逐步重算 embedding。
   - 在线检索会自动按 `embedding_dimension` 过滤，仅检索同维向量。

## 做到了什么
- API 与 Agent Tool 两条检索链路都具备维度守卫。
- 检索返回可直接看到 `retrieval_dimension`，便于排障与监控。
- 维度切换后的“混维窗口期”可以安全运行，不会把不同维度向量混在同一次检索里。

## 效果感知
- 检索日志可见：`dim=...`。
- 检索结果 metadata 可见：`retrieval_dimension`。
- source 检查测试能确保维度过滤条件未被后续改动移除。
