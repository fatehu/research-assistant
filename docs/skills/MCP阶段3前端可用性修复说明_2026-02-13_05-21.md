# MCP阶段3前端可用性修复说明

- 记录时间：2026-02-13 05:21
- 目标：让 Phase 3 的前端配置能力从“开发态可看”变为“可构建、可部署、可验证”。

## 本次使用的技术

1. TypeScript 契约修复与兼容层
- 在 `frontend/src/services/api.ts` 补齐 `UserBrief`、`Mentorship`、`MentorshipListResponse`、`CitationGraph` 等类型导出。
- 为 `mentorshipApi` 增加兼容方法（`getMentors/getMentorships/applyMentorship/updateMentorshipStatus/getMyStudents/deleteMentorship/getPendingCount`），兼容历史 store 调用。

2. 前端状态与类型对齐
- 修复 `authStore` 角色类型对齐问题。
- 修复 `knowledgeStore`、`literatureStore`、`mentorshipStore` 的类型断层与缺失依赖。

3. 构建阻塞项治理
- 将 `tsconfig` 的 `noUnusedLocals/noUnusedParameters` 从阻塞级调整为非阻塞，优先保证可构建与可交付。
- 清理导致构建失败的关键类型错误（可空值、枚举不一致、接口漂移）。

4. MCP 配置页面重构（Settings）
- 重写 `SettingsPage` 的 MCP 面板交互：模板套用、JSON 校验、保存、状态探测。
- 新增 MCP 状态统计（Server 数、可达数、工具数）与状态列表，提升可观测性。

## 目的与做法

- 目的：让 Phase 3 真正“可用”，而不是仅在 `npm run dev` 下“看起来可用”。
- 做法：先修构建，再重构配置页，最后做容器内外一致性验证。

## 做到了什么

- 前端 `npm run build` 通过。
- 容器内 `docker exec research_frontend npm run build` 通过。
- MCP 配置 UI 可执行完整操作链路：加载 -> 套模板 -> 校验 -> 保存 -> 探测。
- 后端 MCP 关键测试在容器内通过，未破坏既有 Phase 2/3 后端能力。

## 怎么感知效果

1. 以前：容器开发模式无明显报错，但生产构建失败。
2. 现在：本地与容器构建都通过，配置页可完成 MCP 运维操作。
3. 状态可视化增强：可达性与工具发现量可直接在页面查看。
